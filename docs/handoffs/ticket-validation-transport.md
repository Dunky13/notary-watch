Candidate 13 completed real app and installer notarization, stapling and final custody. Fresh native acceptance then failed during `stapler validate` when Apple's CloudKit ticket lookup returned `NSURLErrorDomain Code=-1005` and exit 68. The first Intel witness is job 121839430550 in [Distribution 40397392449](https://github.com/Dunky13/notary-watch/actions/runs/40397392449). Final-custody recovery [40400477196](https://github.com/Dunky13/notary-watch/actions/runs/40400477196) preserved identical final files and skipped all five credential-bearing operations, but repeated the transport failure on Intel job 121848388360 and ARM job 121848388483. These failures remain evidence even when a later recovery succeeds.

`nw_validate_ticket` owns bounded validation retries for both the installer and copied app in `verify-macos.sh`. It requires exit 68, the exact observed connection-loss code and the Apple ticket-delivery lookup endpoint, with no authentication-failure diagnostic. It allows three attempts with two-second delays, prints every native diagnostic and returns the final failure unchanged. Missing/invalid tickets, unrelated errors/endpoints and authentication failures cannot gain acceptance. Signature, quarantine, Gatekeeper, installation and native startup gates remain mandatory. The helper never signs, staples, repacks or submits artifacts.

The existing release-output fixture now exercises the real installer-verification call site for both target types. Its transient case failed on the prior source with exit 68 and passes only after a successful third validation. Persistent transport failure exhausts three attempts; invalid tickets, authentication, unrelated CloudKit errors, foreign endpoints, other numeric codes and different exit statuses fail immediately. Existing install-rejection cleanup and transactional output-preservation cases remain covered. These are synthetic regression results, separate from real Apple and hosted qualification.
